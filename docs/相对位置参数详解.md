# 相对位置参数详解

> 本文只讲「参数配置 → 相对位置」这一页签里的每一项：它是什么、怎么填、在代码里驱动了什么、填错会出现什么现象。
> 术语、默认值与单位以源码为准：`backend\src\UavPlatform.Core\Models\RelativeConfig.cs`、
> `backend\src\UavPlatform.Core\Relative\RelativeService.cs`、`backend\src\UavPlatform.Core\Relative\GeoMath.cs`；
> 坐标系术语与 `README.md` 的「五、三维显示坐标系约定」「雷达探测精度校核」两节保持一致。

## 一、这套参数一起解决了什么问题

平台上三个设备给出的观测量落在三个完全不同的坐标系里：

- **基座 UM982**：NMEA 输出 WGS84 经纬高（GGA / RMC），双天线还可以给一条**真航向**（THS）；
- **雷达 NSR**：只知道自己心里的极坐标——目标相对**雷达本体**的距离、方位角、俯仰角（本体约定 +Y 为探测方向、+X 向右、+Z 向上）；
- **无人机 GPS UCM221**：也是 WGS84 经纬高，外加姿态角。

三者不在一个坐标系里，任何「谁在谁哪边」的问题都回答不了。相对位置参数就是那组把差异补齐的输入：**雷达装在哪儿、朝哪儿、姿态如何**，外加**统一坐标系的原点取在哪儿**。

补齐之后，所有结果统一到**以基座为原点的世界 ENU 系（东 X+、北 Y+、天 Z+）**：

- 显示坐标系原点恒为基座，代码里不再提供「以雷达为原点」的选项（`RelativeService.cs:168-173`）；
- 基座与无人机本身就是世界坐标，由 WGS84 → ENU 直接换算；雷达目标由本体极坐标经安装姿态旋转后再平移到雷达位置；
- 这一份结果同时供给：三维/二维/地图显示、`05_frame`（三设备同帧）落盘、`04_radar_base`（雷达转基座系）落盘、平台轨迹，以及无人机 vs 雷达的探测精度校核。

换句话说：**没有这套参数，雷达的目标只能画在雷达自己的坐标系里，无法与 RTK 的绝对位置同框比对**；参数填错通常不报错，而是「所有目标整体转偏 / 整体平移 / 原点悄悄换了地方」。

## 二、参数总表

### 基础（界面顶部，无折叠分组）

| 界面标签 | 配置键（JSON，camelCase） | 类型与单位 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 启用相对位置 | `enabled` | bool | `true` | 相对位置总开关；关掉后不产出相对位置帧，`05_frame` 与 `04_radar_base` **两层落盘一起停** |

> 界面上**没有**「显示坐标系原点」这一项（早期版本的只读文本框、更早的「基座 / 雷达」二选一都已删除，m06173 第 1 点）：显示坐标系恒以基座为原点，`originName` 是常量 `"基座"`（`RelativeService.cs:172`），写进 `RelativeFrame.OriginName`（`RelativeFrame.cs:200-201`）。当前**实际**原点看顶栏的「原点：…」——基座还没定位时它会退化成雷达位置，判断坐标含义要看帧里的 `reference.source`（见 `referenceMode` 的退化分支）。

### 参考点（ENU 原点的取法）

| 界面标签 | 配置键 | 类型与单位 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 参考点来源 | `referenceMode` | 枚举 `auto` / `manual` | `auto` | 原点取基座实测定位，还是取手填经纬度 |
| 手动经度 | `manualLongitude` | number?（度） | `null` | 手动模式下原点经度 |
| 手动纬度 | `manualLatitude` | number?（度） | `null` | 手动模式下原点纬度 |
| 手动海拔（米） | `manualAltitudeM` | number?（米） | `null` | 手动模式下原点海拔；留空按 `0` 米参与解算 |
| 跟随参考点漂移 | `followReferenceDrift` | bool | `false` | 原点锁定后是否允许随基座定位逐帧移动（界面放在「重建节奏与轨迹」组里） |

### 雷达安装（`radar` 对象）

| 界面标签 | 配置键 | 类型与单位 | 默认值 | 作用 |
| --- | --- | --- | --- | --- |
| 安装方式 | `radar.mode` | 枚举 `coLocatedWithBase` / `manualWgs84` / `offsetFromBase` | `coLocatedWithBase` | 雷达位置从哪来 |
| 经度 / 纬度 / 海拔（米） | `radar.longitude` / `radar.latitude` / `radar.altitudeM` | number（度 / 度 / 米） | `0` / `0` / `0` | `manualWgs84` 时的雷达自身 WGS84 定位 |
| 东向偏移 / 北向偏移 / 天向偏移（米） | `radar.offsetEastM` / `radar.offsetNorthM` / `radar.offsetUpM` | number（米，东/北/上为正） | `0` | `offsetFromBase` 时雷达**相对基座**的 ENU 偏移 |
| 雷达朝向来源 | `radar.yawSource` | 枚举 `manualAbsolute` / `baseHeadingPlusOffset` | `baseHeadingPlusOffset` | 雷达正前方方位角怎么来 |

| 横滚角（度） | `radar.rollDeg` | number（度，右倾为正） | `0` | 雷达本体滚转安装角 |

## 三、逐项详解

以下每项都按 **用途 / 取值怎么选 / 代码里驱动了什么 / 设置错了会怎样** 四段说明。

### `enabled`（启用相对位置）

- **用途**：相对位置解算的总闸。
- **取值怎么选**：正常采集保持开启；只想单独存原始/解析数据、不要统一坐标系时关闭。界面 `ConfigPanel.tsx:1213-1221`。
- **代码里驱动了什么**：`Build()` 与 `ProjectRadarToBase()` 双双提前返回 `null`（`RelativeService.cs:139`、`RelativeService.cs:274`）。前者的下游是 `CurrentFrame` 缓存、`TrackStore.Append`、`05_frame` 落盘与 SignalR 推送（`DeviceManager.cs:405-414`）；后者的下游是 `04_radar_base` 落盘（`DeviceManager.cs:471-482`）。
- **设置错了会怎样**：存储页签里「保存雷达转基座系」「保存三设备同帧」两个勾都还打着，但 `04_radar_base/`、`05_frame/` 两个目录都不产生数据，三维视图也拿不到新帧——现象是「设备数据正常、三维不更新」，很容易误判成前端问题。

### `referenceMode`（参考点来源）

- **用途**：决定 ENU 切平面原点取哪个大地坐标。
- **取值怎么选**：`auto`（默认）取基座第一个有效定位结果，基座还没定位时**退化为雷达位置**；`manual` 用下面三个手动字段，用于基座暂未定位先跑起来，或复现历史数据。界面选项文案为「自动（取基准设备定位）」/「手动指定」（`ConfigPanel.tsx:1238-1239`）。
- **代码里驱动了什么**：`ResolveReference()` 的优先级是 手动 → 基座 → 雷达（`RelativeService.cs:393-445`），解析结果写进 `RelativeFrame.Reference` 并作为 `GeoMath.GeodeticToEnu` 的切平面原点（`RelativeService.cs:447-448`）。因为原点就是切平面原点，**被选设备自己的 ENU 恒为 (0,0,0)**（`RelativeService.cs:175-176`）。
- **设置错了会怎样**：选 `manual` 但经纬度没填全时，手动分支不成立（要求经纬度**同时非空**且通过合理性检查，`RelativeService.cs:406-408`），会退回自动逻辑，看起来「手动没生效」；原点一旦解析成功就被**锁死**（默认 `followReferenceDrift = false`，`RelativeService.cs:402`），后续基座移动不再改变原点，只表现为基座节点偏离原点。保存配置时若本项或三个手动坐标发生变化，`DeviceManager` 会调用 `ResetReference()` 让原点重新锁定（`DeviceManager.cs:228-241`），另有 REST `POST /relative/reset-reference`（`Program.cs:147-151`）。

### `manualLongitude` / `manualLatitude` / `manualAltitudeM`（手动参考点）

- **用途**：手填原点经纬高，仅在 `referenceMode = manual` 时有意义。
- **取值怎么选**：经纬度按 WGS84 十进制度录入（界面 `step="any"`），海拔单位米。**经纬度必须成对填写**；海拔留空按 `0` 米处理。
- **代码里驱动了什么**：通过 `IsPlausible()` 检查后成为 `GeoReference`，`source = "Manual"`（`RelativeService.cs:410-417`）。检查条件：非 NaN、`|lat| ≤ 90`、`|lon| ≤ 180`、且**不能同时为 0**（`RelativeService.cs:450-453`）。海拔走 `settings.ManualAltitudeM ?? 0`（`RelativeService.cs:414`）。
- **设置错了会怎样**：经纬度填 `0, 0` 被判定不合理，手动分支不生效；只填经度不填纬度同样不生效；海拔留空但经纬度填了时，原点海拔按 0 米算，全部目标的 `up` 会整体带一个固定高度差——现象是「相对高度普遍偏高/偏低一个常数值」。界面提示「留空表示不指定（写 null），不会被当成 0」对**经纬度**成立，对**海拔**不成立。

### `followReferenceDrift`（跟随参考点漂移）

- **用途**：原点锁定后是否允许它随基座定位逐帧移动。
- **取值怎么选**：默认 `false`（锁定），保证轨迹参考系稳定；只有「基座本身会移动（车载/船载），希望基座永远画在原点」时才置 `true`。界面见 `ConfigPanel.tsx:1630-1638`。
- **代码里驱动了什么**：`ResolveReference()` 的第一行——`if (_reference.Resolved && !settings.FollowReferenceDrift) return _reference;`（`RelativeService.cs:402`）。置 `true` 后每帧重新走一遍候选解析。
- **设置错了会怎样**：`false` 时基座定位漂移是**可见**的（基座节点带一个变化的 ENU 偏移）；置 `true` 后原点每帧重新贴在基座当前位置上，基座恒在 (0,0,0)，**漂移被吸收进雷达与无人机的坐标**里，历史轨迹跨帧不再可比。候选解析失败（`candidate` 为 null）时 `_reference` 保持不变、不覆盖（`RelativeService.cs:442-443`），也就是不会退回上一个候选，只是停止跟随。

### `radar.mode`（雷达安装方式）

- **用途**：决定雷达在 ENU 里的位置从哪来。
- **取值怎么选**：`coLocatedWithBase`（默认）雷达与基座天线共址，位置即基座位置（`RelativeService.cs:375-380`）；`manualWgs84` 雷达自带定位或人工测得经纬度（`RelativeService.cs:361-364`）；`offsetFromBase` 现场皮尺量出的相对偏置（`RelativeService.cs:366-373`）。界面选项为「与基座共址」/「手动经纬高」/「相对基座偏移」（`ConfigPanel.tsx:1302-1304`）。
- **代码里驱动了什么**：`ResolveRadar()` 产出雷达大地坐标再换算成 `radarEnu`；`RadarBaseLineM`（雷达—基座基线长度）来自这两点之间的距离（`RelativeService.cs:236-238`）；目标最终位置是 `radarEnu + 旋转后的本体向量`（`RelativeService.cs:588`）。节点 `note` 会注明位置来源：「雷达位置：与基座共址」/「雷达位置：基座 + 偏移」/「雷达位置：手动经纬度」（`RelativeService.cs:363`、`371`、`378`）。
- **设置错了会怎样**：选共址或偏移而基座还没有定位时，`ResolveRadar()` 返回 `null`，雷达节点 `note` 变成「雷达位置未确定：请选择安装位置方式（共址 / 相对基座偏移 / 手动经纬度）」（`RelativeService.cs:509-511`），雷达坐标为 (0,0,0)，三维里雷达与所有目标堆在原点附近；选 `manualWgs84` 但经纬度仍是默认 `0, 0` 时 `IsPlausible` 判定不合理，同样返回 `null`；偏移量方向填反（东/北）时雷达与全部目标整体反方向平移，偏差大小正好是偏移量的两倍。

### `radar.longitude` / `radar.latitude` / `radar.altitudeM`（雷达独立定位）

- **用途**：只在 `manualWgs84` 时参与解算，给出雷达自身的 WGS84 位置。
- **取值怎么选**：WGS84 十进制度 + 海拔米。雷达自带 RTK 时直接抄；人工测量时用移动站实测。界面只在 `manualWgs84` 下显示这一组输入框（`ConfigPanel.tsx:1309-1351`）。
- **代码里驱动了什么**：直接作为雷达大地坐标参与 `GeodeticToEnu`，并写进雷达节点的 `latitude/longitude/altitudeM`（`RelativeService.cs:499-501`）。
- **设置错了会怎样**：位置写偏 N 米，则雷达与**所有雷达目标**一起平移 N 米（因为目标 = 雷达位置 + 本体向量）；与无人机 RTK 的比对偏差也随之被算错——校核页的 `deltaEastM`/`deltaNorthM` 会出现一个恒定偏置，这是发现「坐标填错了」的最快途径。

### `radar.offsetEastM` / `radar.offsetNorthM` / `radar.offsetUpM`（相对基座偏移）

- **用途**：只在 `offsetFromBase` 时参与解算，描述雷达相对**基座**的东北天偏移。
- **取值怎么选**：皮尺量基座天线到雷达的距离并分解为东/北/天三分量（东为正、北为正、上为正）。注意偏移是**相对基座**，不是相对显示原点。界面见 `ConfigPanel.tsx:1353-1395`。
- **代码里驱动了什么**：`GeoMath.EnuToGeodetic(offset, 基座经纬高)` 把偏移折成雷达的绝对经纬高（`RelativeService.cs:369-372`）。
- **设置错了会怎样**：与 `manualWgs84` 填错同量级——雷达与全部目标整体错位；另外基座定位本身有漂移时，雷达位置会跟着漂，现象是「雷达点一直在小幅移动」，这是该模式的固有特性而非故障。

### `radar.yawSource`（雷达朝向来源）

- **用途**：决定「雷达正前方（本体 +Y）」相对正北的方位角从哪里取，这是全部目标方位的关键输入。
- **取值怎么选**：`baseHeadingPlusOffset`（默认，推荐）＝ `正前方 = 基座双天线基线真航向(THS) + 相对基线夹角`，随基座实时更新，现场只量一个安装夹角，基座转动或天线重新架设都不必重填；`manualAbsolute` ＝ 直接填相对正北的绝对角，用作双天线不可用时的兜底（`ConfigPanel.tsx:1418-1419`）。
- **代码里驱动了什么**：`RadarPlacementSettings.ResolveYawDeg()`（`RelativeConfig.cs:95-106`）。只有来源为 `baseHeadingPlusOffset`、`baselineHeadingDeg` 非空且 `headingSource == "THS"`（忽略大小写）时才走基线分支，返回 `Normalize360(基线航向 + 夹角)` 且 `FromBaseline = true`；否则一律返回 `Normalize360(yawDeg)`。帧里用 `radarBoresightFromBaseline` 如实记录本帧用的是哪一支（`RelativeService.cs:189-190`、`RelativeService.cs:239-241`），雷达节点的 `headingDeg` 也直接取该结果（`RelativeService.cs:502`）。
- **设置错了会怎样**：选 `baseHeadingPlusOffset` 但基座没接双天线、或收到的航向来源是 RMC/VTG，会**静默回落**到 `yawDeg`；若 `yawDeg` 还是 0，则所有目标被当成在正北方向，整体旋转错位——现象是「目标方位角系统性偏一个固定角度，无人机 RTK 与雷达回波的水平偏差巨大」。反过来，选 `manualAbsolute` 却指望它自动跟踪基座转动时，基座一动全部目标跟着错。

### `radar.yawOffsetFromBaselineDeg`（相对基线夹角）

- **用途**：双天线模式下唯一需要现场量的角度：雷达正前方相对**基座两根天线连成的基线**偏了多少。`0` = 与基线同向，`180` = 反向，顺时针为正。
- **取值怎么选**：现场量出雷达探测方向与基座主副天线连线方向的夹角。界面这一项仅在 `yawSource = baseHeadingPlusOffset` 时可用，否则 `disabled`（`ConfigPanel.tsx:1435`）。
- **代码里驱动了什么**：直接参与 `Normalize360(heading + YawOffsetFromBaselineDeg)`（`RelativeConfig.cs:102`），结果写入帧的 `radarBoresightDeg`，并作为 `GeoMath.RotateRadarToEnu` 的 yaw 参数（`RelativeService.cs:585`）。
- **设置错了会怎样**：夹角错 θ 度，所有雷达目标的方位角整体旋转 θ（目标云团被拧着转），而距离与俯仰基本不变；最容易与「雷达安装本身装偏了」混淆。

### `radar.yawDeg`（探测方向，相对正北）

- **用途**：手动绝对角；在双天线模式下它是**兜底值**。`0` = 朝正北，`90` = 朝正东。
- **取值怎么选**：现场用罗盘或地图量取。双天线模式下界面把它调暗但仍可编辑（`ConfigPanel.tsx:1459-1461`），目的就是让现场先把兜底值填好，THS 一断立刻有值可用。
- **代码里驱动了什么**：`ResolveYawDeg()` 的非基线分支（`RelativeConfig.cs:105`），以及 `manualAbsolute` 模式下的唯一来源。
- **设置错了会怎样**：只影响「本帧没有可用 THS」的帧。典型现象是「THS 正常时目标位置正确，基座一重启或双天线一断，目标瞬间整体转偏」——此时切到的正是这个兜底角。

### `radar.pitchDeg` / `radar.rollDeg`（雷达安装俯仰 / 横滚）

- **用途**：雷达本体的安装姿态角，抬头为正、右倾为正。
- **取值怎么选**：默认 `0`（水平正装）。雷达用支架上仰/下俯或侧倾安装时按实际填写；界面不做参数联动，始终可编辑（`ConfigPanel.tsx:1471-1496`）。
- **代码里驱动了什么**：两者与 `boresightDeg` 一起进入 `GeoMath.RotateRadarToEnu`，旋转顺序固定为 **Roll（绕本体 Y）→ Pitch（绕本体 X）→ Yaw（绕天向）**（`GeoMath.cs:174-202`）；同时原样写进雷达节点的 `pitchDeg`/`rollDeg` 供界面显示（`RelativeService.cs:503-504`）。速度矢量用同一套参数旋转，不做平移（`RelativeService.cs:590-591`）。
- **设置错了会怎样**：俯仰填错会让目标的水平距离与高度同时错（近处目标往远/近偏、高度整体抬/降）；横滚填错在目标接近正前方时影响小、在两侧大方位角时影响明显。

### `filter.maxRangeM`（最大距离）

- **用途**：按**相对雷达的斜距**过滤目标。
- **取值怎么选**：默认 `0` = 不限；想只看近区就填实际关心的半径（米）。判定用的是雷达报的 `Range`，不是换算后的 ENU 距离。
- **代码里驱动了什么**：`if (filter.MaxRangeM > 0 && t.Range > filter.MaxRangeM) continue;`（`RelativeService.cs:574`）。
- **设置错了会怎样**：填得比无人机实际斜距还小，**无人机回波会被一起滤掉**，校核结果从「有偏差」直接变成 `droneComparison = null`（对比要求 `targets.Length > 0`，`RelativeService.cs:641`）——现象是「勾了对比却一直没有数据」。

### `filter.minSnr`（最低 SNR）

- **用途**：按信噪比过滤，用于压掉弱杂波。
- **取值怎么选**：默认 `0` = 不限；取值要结合现场杂波水平试。
- **代码里驱动了什么**：`if (filter.MinSnr > 0 && t.Snr < filter.MinSnr) continue;`（`RelativeService.cs:575`）。
- **设置错了会怎样**：门槛过高会把真实小目标（含无人机）整片滤掉；与 `maxRangeM` 一样让对比变成 `null` 而不是报错。

### `filter.dropDeleted`（丢弃已删除目标）

- **用途**：丢掉协议显式标记为「已删除」的目标（`type = 0xFFFF`，`Telemetry.cs:158-159`）。
- **取值怎么选**：默认开启；想原样看到协议里的删除标记时才关闭。
- **代码里驱动了什么**：`if (filter.DropDeleted && t.Type == RadarTargetTypes.Deleted) continue;`（`RelativeService.cs:573`）。
- **设置错了会怎样**：关掉后这些目标会以「已删除」类型出现在三维视图与 `05_frame` 里，看起来像幽灵目标。注意它**只影响相对位置输出**：`02_radar` 的原始与解析文件始终全量保存（`RelativeConfig.cs:111`、`RelativeConfig.cs:123-127`）。

### `filter.maxTargets`（最多目标数）

- **用途**：限制单帧相对位置里的目标/点云点数量，避免点云帧把显示与落盘打爆。
- **取值怎么选**：默认 `4000`，`0` 表示不限。点云帧点数动辄上千，不建议关掉限制。
- **代码里驱动了什么**：`var max = filter.MaxTargets > 0 ? filter.MaxTargets : int.MaxValue;`（`RelativeService.cs:568`），循环末尾 `if (list.Count >= max) break;`（`RelativeService.cs:625`）。`04_radar_base` 复用同一套构建逻辑，因此同受该上限约束（`RelativeConfig.cs:123-127`）。
- **设置错了会怎样**：截断按**雷达帧内的顺序**取前 N 个，不是按距离/信噪比排序取最好的 N 个——设小了可能正好把无人机回波排在门外，导致对比失效；三维视图里的目标数会突兀地卡在一个固定值。

### `comparison.enabled`（启用无人机 vs 雷达探测对比）

- **用途**：把无人机当成天上飞的运动靶标，用它的 RTK 位置校核雷达的测角/测距精度。
- **取值怎么选**：默认开启；不做校核时关掉可省下这部分计算（界面 `ConfigPanel.tsx:1558-1566`）。
- **代码里驱动了什么**：`BuildDroneComparison()` 的第一道门（`RelativeService.cs:640`）。关闭后 `RelativeFrame.DroneComparison` 为 `null`（`RelativeFrame.cs:251-252`）。
- **设置错了会怎样**：只影响这一字段；无人机位置、目标位置照常解算。

### `comparison.matchRadiusM`（匹配半径）

- **用途**：在雷达目标里取离无人机 RTK 位置**最近**的一个当作「无人机回波」，两者三维距离超过该半径即认为本帧雷达没探到无人机。
- **取值怎么选**：默认 `20` 米，要结合雷达点位精度与无人机 RTK 精度选：太小则大量帧被判为「未匹配」，太大则可能匹配到旁边的干扰物。
- **代码里驱动了什么**：`var radius = Math.Max(0, compare.MatchRadiusM);`（`RelativeService.cs:644`），最近点按三维距离比较（`RelativeService.cs:649-660`），`Matched = nearestDistance <= radius`（`RelativeService.cs:678`），实际使用的半径回填进 `matchRadiusM` 字段（`RelativeService.cs:679`）。
- **设置错了会怎样**：即使 `Matched = false`，返回的记录里**仍然带着最近目标的 id 与各项偏差**（函数不会提前返回，`RelativeService.cs:662-703`），所以读数前必须先看 `matched`；把半径设成 0 时只有完全重合才算匹配。

### `relativeIntervalMs`（相对位置间隔）

- **用途**：出帧限频，防止高频设备（尤其是雷达点云）把相对位置输出打爆。
- **取值怎么选**：默认 `100` 毫秒（10 Hz），`0` = 不限频。
- **代码里驱动了什么**：`Build()` 用 `Environment.TickCount64` 做滑动窗口判断，被丢弃的帧计入 `SuppressedFrames`（`RelativeService.cs:141-152`）；定时器每 200 毫秒也会调一次 `Build("timer")`（`DeviceManager.cs:485-506`），所以设备静默时也照常出帧并刷新超时状态。`force = true`（REST `POST /relative/force`、`DeviceManager.ForceRebuild`）绕过限频，但不更新限频时间戳。
- **设置错了会怎样**：填得过小，点云帧会把显示与 `05_frame` 写爆；填得过大（比如 2000）三维视图会明显卡顿式跳动。注意它**不影响 `04_radar_base`**——那一层按雷达帧逐帧写，一条不落（`DeviceManager.cs:466-470`、`SessionStorage.cs:334`）。

### ~~`trackHistorySeconds`（轨迹保留）~~ —— 已删除，并入「尾迹时长」

- **它原来是干什么的**：无人机轨迹与各雷达目标拖尾的保留时长，供前端**刷新页面后**回看历史轨迹。
- **为什么删**（m06464 第 5 点）：它与工具条上的**尾迹时长**（`ui.trailSeconds`）是同一个意思
  （轨迹在屏幕上活多久），两个旋钮必然对不上——尾迹拉到 600 s、后端只留 60 s，刷新页面就只能回看 60 s。
  按现场要求只留尾迹那一个输入，删掉这个参数。
- **现在怎么算**：后端的保留窗口由尾迹时长推出——`DeviceManager.TrackRetention(int trailSeconds)`
  返回 `(Math.Clamp(trailSeconds, 30, 600), Math.Max(10, 秒数 × 5))`，再交给
  `TrackStore.Configure(保留秒数, 每条轨迹点数上限, 300)`（构造走 `BuildTrackStore(trailSeconds)`，
  热应用走 `ApplyTrackRetention(trailSeconds)`）。界面上改尾迹走 `PUT /api/config/ui`，
  `PlatformService.SaveUiAsync` 顺手调一次 `ApplyTrackRetention`，**不重启采集管线**。
- **为什么下限是 30 秒**：尾迹填 0 时屏幕不画尾迹，但刷新后仍要能回看半分钟；跟踪目标数上限固定 300，不可配。
- **旧配置还能用**：`ConfigJson.Options` 没开 `UnmappedMemberHandling.Disallow`，旧 `platform.json` /
  `session.json` 里残留的 `"trackHistorySeconds": 60` 会被**忽略**，不会导致加载失败。

### `staleTimeoutMs`（数据陈旧阈值）

- **用途**：设备数据超过该时长未更新，就在该设备节点上标记为不新鲜。
- **取值怎么选**：默认 `3000` 毫秒，要覆盖设备自身的输出周期（雷达、RTK 的报数间隔不同）。
- **代码里驱动了什么**：`var stale = Math.Max(500, settings.StaleTimeoutMs);`（`RelativeService.cs:161`，`ProjectRadarToBase` 同式 `RelativeService.cs:305`），随后在 `MakeGnssNode` / `MakeRadarNode` / `MakeDroneNode` 里用 `fresh = sample is not null && ageMs <= stale` 计算节点 `Fresh`，并把「数据已超时」写进节点 `note`（`RelativeService.cs:462-463`、`RelativeService.cs:551-557`）。
- **设置错了会怎样**：填得比设备报数周期还小，节点会长期显示「数据已超时」，但**帧照出、目标照算、落盘照写**——陈旧判定只打标记（`RelativeConfig.cs:190`）。填小于 500 的值会被抬到 500，界面上填的数和实际生效值不一致。

## 四、角度与轴的约定

- **显示坐标系（世界 ENU）**：东 X+、北 Y+、天 Z+。three.js 里的轴映射是 **x = 东、y = 天、z = −北**，于是屏幕上方是正北、右方是正东（README.md:246）。
- **雷达本体系**：**+Y 为探测方向、+X 向右、+Z 向上**（`GeoMath.cs:169-173`）。
- **方位角**：一律**相对正北、顺时针为正**，统一由 `GeoMath.Normalize360` 归一到 `[0, 360)`；比较两个方位角之差时用 `Normalize180` 归一到 `(-180, 180]`（`GeoMath.cs:47-60`）。
- **俯仰角**：抬头为正；**横滚角**：右倾为正。
- **旋转顺序**：Roll（绕本体 Y）→ Pitch（绕本体 X）→ Yaw（绕天向）。Yaw 这一步把本体 +Y 转到正北、本体 +X 转到正东，落在 ENU 上的表达式是
  `east = x₂·cos(yaw) + y₂·sin(yaw)`，`north = −x₂·sin(yaw) + y₂·cos(yaw)`，`up = z₂`（`GeoMath.cs:194-199`）。
- **逆变换** `GeoMath.EnuToRadarBody` 顺序相反（−Yaw → −Pitch → −Roll），用于把无人机 RTK 位置换算成雷达本体系的「真值极坐标」（`GeoMath.cs:204-238`）。
- **极坐标 ↔ 直角坐标**：`x = R·cos(el)·sin(az)`、`y = R·cos(el)·cos(az)`、`z = R·sin(el)`；反解 `az = atan2(x, y)`、`el = asin(z/R)`（`GeoMath.cs:240-257`）。

## 五、解算链路（一帧是怎么算出来的）

触发源有两种：任一设备样本到达（`_relative.Build($"device:{kind}")`，`DeviceManager.cs:424`）、200 毫秒定时器（`timer`，`DeviceManager.cs:480`）。

1. **总闸与限频**：`enabled` 为假直接返回 `null`；否则按 `relativeIntervalMs` 判断本帧是否放行（`RelativeService.cs:139-152`）。
2. **三设备定位**：基座 `ResolveBase()` 要求 `fix.Valid` 且经纬度通过 `IsPlausible`，海拔为 `AltitudeM ?? 0`（`RelativeService.cs:345-351`）；雷达 `ResolveRadar()` 按 `radar.mode` 三选一（`RelativeService.cs:353-382`）；无人机 `ResolveDrone()` 与基座同规则（`RelativeService.cs:384-390`）。
3. **参考点解析**：`ResolveReference()` 依次尝试 手动坐标 → 基座定位 → 雷达定位；已锁定且不跟随漂移时直接复用旧原点（`RelativeService.cs:393-445`）。
4. **ENU 换算**：以参考点为切平面原点，`GeoMath.GeodeticToEnu` 内部走 ECEF（`GeoMath.cs:63-130`）。参考点未解析时三个 ENU 全为 0（`RelativeService.cs:176-184`）。
5. **雷达正前方解算**：基线航向取 `baseSample.TrueHeadingDeg` 并归一化（`RelativeService.cs:188`），交给 `ResolveYawDeg()` 得到 `boresightDeg` 与 `boresightFromBaseline`（`RelativeConfig.cs:95-106`）；结果写入 `radarBoresightDeg` / `radarBoresightFromBaseline` / `radarBaselineHeadingDeg`（`RelativeFrame.cs:221-228`）。
6. **目标本体直角坐标**：优先用协议给的 `X/Y/Z`；三个都为 0 而距离大于 0 时按极坐标换算（`RelativeService.cs:577-582`）。
7. **本体 → ENU**：`GeoMath.RotateRadarToEnu(x, y, z, boresightDeg, pitchDeg, rollDeg)`；参考点未解析时该向量取零（`RelativeService.cs:584-586`）。
8. **平移到雷达位置**：`position = radarEnu + delta`（`RelativeService.cs:588`）；速度矢量用同一旋转、不做平移（`RelativeService.cs:590-591`），合速度取三分量模（`RelativeService.cs:618-620`）。
9. **过滤**：`dropDeleted` → `maxRangeM` → `minSnr` 三道逐条筛，最后受 `maxTargets` 截断（`RelativeService.cs:571-626`）；同时给每个目标附上与无人机的三维距离与高度差（`RelativeService.cs:593-599`）。
10. **无人机对比**：取离 RTK 位置最近的雷达目标，偏差定义为**雷达 − RTK**：`ΔE = 目标.East − 无人机.East`（North/Up 同式），`Δ三维 = √(ΔE²+ΔN²+ΔU²)`，`Δ水平 = √(ΔE²+ΔN²)`（`RelativeService.cs:664-693`）。再把 RTK 位置用 `EnuToRadarBody` 反旋回雷达本体系、转成极坐标，得到一组「真值极坐标」，与雷达实测值相减：`ΔRange = 雷达距离 − RTK距离`、`ΔAz = Normalize180(雷达方位 − RTK方位)`、`ΔEl = 雷达俯仰 − RTK俯仰`（`RelativeService.cs:669-702`）。
11. **平台量**：`droneDistanceToBaseM`（水平距离）、`droneHeightAboveBaseM`（天向差）、`droneDistanceToRadarM`（三维）、`radarBaseLineM`、`baseToDroneSkewMs`（基座与无人机样本的时间差，衡量时间一致性）（`RelativeService.cs:210-224`、`RelativeService.cs:236-238`）。
12. **出帧与下游**：`FrameReady` 事件带出帧——`DeviceManager` 更新 `CurrentFrame`、追加轨迹、写 `05_frame`（整帧序列化为一行 JSON，含 `targets` 与 `droneComparison`，`SessionStorage.cs:343-356`）、再经 `RelativeFrameReady` → `LiveBroadcaster`（`LiveBroadcaster.cs:61`）推送前端三维显示。另有一条**独立于出帧限频**的路径：每收到一帧雷达数据就调 `ProjectRadarToBase()`，把该帧每个目标换算到以基座为原点的 ENU 写入 `04_radar_base`；基座未定位时 `baseResolved = false`，只保留距离/方位/俯仰等本体观测量，直角坐标字段为 0，不丢数据（`DeviceManager.cs:466-482`、`RelativeService.cs:265-329`、`RelativeFrame.cs:259-264`）。

## 七、常见配置组合

| 现场 | 参数怎么填 | 能看到什么 | 注意什么 |
| --- | --- | --- | --- |
| **雷达与基座同址**（默认，最省事） | `radar.mode = coLocatedWithBase`；`yawSource = baseHeadingPlusOffset` + 量一个 `yawOffsetFromBaselineDeg`；`pitchDeg`/`rollDeg` 按实际安装 | 雷达节点落在原点（与基座重合），`radarBaseLineM = 0`；目标由安装夹角直接旋到基座系；基座转动时目标云团不跟着乱转 | 必须有基座定位，否则雷达位置解析不出来；必须收到 **THS**，否则回落到 `yawDeg` 兜底 |
| **雷达异地、有独立坐标** | `radar.mode = manualWgs84` + 填 `longitude`/`latitude`/`altitudeM`；朝向推荐双天线基线夹角（雷达与基座同一刚体时） | 雷达节点显示在真实偏移处，`radarBaseLineM` 等于实测基线长；目标相对基座的方位完全由雷达自身朝向决定 | 雷达与基座**不在同一刚体**时不能再用「基线航向 + 夹角」——基线一转头目标会整体转错，此时应改 `manualAbsolute` + `yawDeg`；坐标填错 N 米，全部目标平移 N 米 |
| **雷达只有相对基座的偏置** | `radar.mode = offsetFromBase` + 填东/北/天三个偏移（皮尺量） | 与共址类似，只是雷达节点偏移到实测位置；目标位置 = 基座 + 偏移 + 旋转后的本体向量 | 偏移是相对**基座**、不是相对显示原点；基座定位漂移会带着雷达位置一起漂；基座无定位时该模式直接不可用 |
| **基座还没定位，只有手动参考点** | `referenceMode = manual` + 同时填 `manualLongitude`/`manualLatitude`（`manualAltitudeM` 建议一并填，否则按 0 米）；雷达必须用 `manualWgs84`（共址与偏移都依赖基座定位）；`yawSource` 只能用 `manualAbsolute` | 原点固定在手填点上，雷达目标可以正常显示为该点附近的 ENU 坐标；`reference.source = "Manual"` | 基座节点因没有定位而**画在原点**（`baseEnu` 保持零），但它并不真的在原点上；此时基座相关的相对量（`droneDistanceToBaseM`、`radarBaseLineM`）都没有意义 |

## 八、自查：怎么快速确认参数填对了

- **看 `radarBoresightFromBaseline`**：`true` 说明本帧用的是 THS 基线航向；`false` 时再看 `radarBaselineHeadingDeg`——有值说明收到了航向但来源不是 THS（RMC/VTG 被拒），为 `null` 说明根本没收到定向。基座节点 `note` 会直接写「航向来自 RMC / VTG / THS」（`RelativeService.cs:551-557`）。
- **看 `radarBaseLineM`**：共址模式必须是 0；`manualWgs84` / `offsetFromBase` 下应等于实测基线长度，对不上就是坐标或偏移填错了。
- **看 `droneComparison.deltaEastM` / `deltaNorthM` 的分布**：恒定偏置 ⇒ 雷达位置或朝向参数填错；随机散布 ⇒ 雷达真实探测误差。再看 `rtkRangeM` 与 `radarRangeM`、`rtkAzimuthDeg` 与 `radarAzimuthDeg`，可以区分是测距问题还是测角问题。
- **看节点 `note`**：会给出「雷达位置未确定：请选择安装位置方式…」「数据已超时」「未收到基座定位数据」等明确原因（`RelativeService.cs:509-511`、`RelativeService.cs:551-557`）。
- **看 `reference.source`**：`Manual` / `基座` / `雷达` 三种取值，确认原点是不是你以为的那个。

## 九、参数生效条件与联动

| 参数 | 什么条件下才真正参与解算 | 条件不满足时 |
| --- | --- | --- |
| `referenceMode = manual` + 三个手动坐标 | 经纬度**同时非空**且通过 `IsPlausible`（`\|lat\| ≤ 90`、`\|lon\| ≤ 180`、不能同时为 0） | 退回自动逻辑：基座 → 雷达 |
| `followReferenceDrift` | 仅当原点已解析时才有区别（未解析时本来每帧都要重新找） | —— |
| `radar.longitude` / `latitude` / `altitudeM` | 仅 `radar.mode = manualWgs84` | 值留在配置里但不参与解算 |
| `radar.offsetEastM` / `offsetNorthM` / `offsetUpM` | 仅 `radar.mode = offsetFromBase`，且基座已定位 | 其他安装方式下不用；基座无定位时雷达位置解析为 `null` |
| `radar.yawOffsetFromBaselineDeg` | 仅 `radar.yawSource = baseHeadingPlusOffset` **且本帧收到的航向来源是 THS** | 该帧改用 `radar.yawDeg` |
| `radar.yawDeg` | `manualAbsolute` 模式，或双天线模式下本帧没有可用 THS | THS 正常时不参与解算（仍建议填好兜底值） |
| `radar.pitchDeg` / `rollDeg` | 始终参与目标与速度矢量的旋转 | 参考点未解析时整个旋转结果取零 |
| `filter.maxRangeM` / `minSnr` | 仅当值大于 0 时过滤 | `0` = 不过滤 |
| `filter.maxTargets` | 仅当值大于 0 时截断 | `0` = 不限 |
| `comparison.matchRadiusM` | 需 `comparison.enabled`、参考点已解析、无人机有定位、过滤后目标非空 | 对比结果整体为 `null` |
| `relativeIntervalMs` | 仅当值大于 0 时限频；`force = true` 的调用绕过 | `0` = 每收到一帧设备数据都出帧 |
| `staleTimeoutMs` | 实际生效值 = `Math.Max(500, 配置值)` | 小于 500 的配置被抬到 500 |
| 工具条「尾迹」（`ui.trailSeconds`） | `0` = 屏幕不画尾迹；后端仍保留 30 秒供刷新回看，每轨点数上限 `Math.Max(10, 秒数 × 5)` | 界面工具条 |

界面侧还有一层联动：`手动经度/纬度/海拔` 仅在 `参考点来源 = 手动指定` 时出现（`ConfigPanel.tsx:1245-1288`）；`雷达安装` 下的经纬高、偏移两组输入框各自只在对应安装方式下出现（`ConfigPanel.tsx:1309-1395`）；`相对基线夹角` 在非双天线模式下被 `disabled`，而 `探测方向` 只是调暗、不禁用（`ConfigPanel.tsx:1432-1470`）。

## 十、落盘分工：哪些参数影响哪一层数据

| 数据层 | 由谁控制 | 受哪些相对位置参数影响 | 是否受出帧限频 |
| --- | --- | --- | --- |
| `01_base_station` / `02_radar` / `03_drone_gps` 的 raw 与 parsed | 设备卡片的「保存原始数据」+ 存储页签 | 不受相对位置参数影响，始终全量 | 不受 |
| `04_radar_base`（每帧雷达一条，目标换算到基座系） | 存储页签「保存雷达转基座系」+ `enabled` | `radar.mode`、`yawSource`/`yawOffsetFromBaselineDeg`/`yawDeg`、`pitchDeg`/`rollDeg`、`filter.*` | **不受**，按雷达帧逐帧写（`DeviceManager.cs:466-470`、`SessionStorage.cs:334`） |
| `05_frame`（每出一帧一条，含 `targets` 与 `droneComparison`） | 存储页签「保存三设备同帧」+ `enabled` | 上述全部，外加 `referenceMode`/`manual*`/`followReferenceDrift`、`comparison.*` | 受 `relativeIntervalMs`（`SessionStorage.cs:343-356`） |
| 三维 / 二维 / 地图显示 | 常开 | 与 `05_frame` 同源，经 SignalR 推送（`LiveBroadcaster.cs:61`） | 同上 |
| 平台轨迹（`GET /tracks`、Hub 下发） | 常开 | 由出帧的点累积，长度由工具条「尾迹」`ui.trailSeconds` 决定（夹 30~600 秒，`Program.cs:65-71`、`TrackStore.cs`） | 同上 |

## 十一、现场填写顺序（推荐）

1. **先定参考点**：基座能定位就保持 `auto`；不能就切 `manual`，经纬度成对填写，海拔一并填（否则按 0 米参与解算）。
2. **再定雷达位置**：与基座共址用默认 `coLocatedWithBase`；量得出相对位置用 `offsetFromBase`；有独立坐标用 `manualWgs84`。
3. **再定朝向**：能收到 THS 就用 `baseHeadingPlusOffset`，只需量一个相对基线夹角；同时把 `yawDeg` 填成可信的绝对角作为兜底。雷达与基座不在同一刚体上时直接用 `manualAbsolute`。
4. **最后填安装姿态**：`pitchDeg` / `rollDeg` 按实际支架角度填写。
5. **过滤先全放开**（`maxRangeM = 0`、`minSnr = 0`），确认目标和无人机回波都能看到，再逐步收紧。
6. **用校核读数反查前四步**：`droneComparison` 的偏差若是恒定偏置，问题在位置或朝向参数；若是随机散布，那才是雷达自身的探测误差。

## 十二、易踩的坑（均已在源码中确认）

1. **自动模式下基座没定位，原点会悄悄变成雷达位置。** `ResolveReference()` 的第三个候选是雷达坐标（`RelativeService.cs:173`、`RelativeService.cs:430-440`），而且一旦解析成功就锁定（`RelativeService.cs:402`）。基座后来拿到定位，原点也不会自动回到基座——现象是「基座节点一直显示一个固定的偏移量」。
2. **天线航向只有 THS 被采纳。** RMC / VTG 给的是航迹向，基座静止时就是噪声，`ResolveYawDeg()` 明确只接受 `headingSource == "THS"`（`RelativeConfig.cs:97-105`；NMEA 侧三种来源分别标记为 `"RMC"`/`"VTG"`/`"THS"`，`NmeaProtocol.cs:262-263`、`282-283`、`300-301`）。没有 THS 时静默回落到 `yawDeg`，**不报错**——所以现场务必先把 `yawDeg` 填成可信的兜底值。
3. **`staleTimeoutMs` 管的是「新鲜标记」，不是「用不用这份数据」。** 陈旧判定用超时窗口（`ageMs <= Math.Max(500, StaleTimeoutMs)`），与 `relativeIntervalMs` 各管各的：限频只决定「这一帧出不出」，超时只决定节点上打不打「数据已超时」（`RelativeService.cs:161`、`RelativeService.cs:462-463`、`RelativeService.cs:551-557`）。设备断线后旧样本仍会参与解算并照常落盘，直到有新样本覆盖。
4. **过滤参数会把无人机回波一起滤掉。** `maxRangeM` / `minSnr` / `maxTargets` 都作用在同一份目标列表上，而对比要求过滤后目标非空（`RelativeService.cs:571-626`、`RelativeService.cs:641`）。所以「对比突然没数据了」的第一嫌疑是过滤参数，而不是对比功能本身。
5. **`maxTargets` 是「取前 N 个」而非「取最好的 N 个」。** 截断发生在循环末尾（`RelativeService.cs:625`），顺序就是雷达帧内的顺序；点云帧尤其容易因此丢掉靠后的真实目标。
6. **`matched = false` 的对比记录里照样有 id 和偏差。** 函数在未匹配时并不提前返回（`RelativeService.cs:662-703`），读数前先看 `matched`（`RelativeFrame.cs:124-126`）。
7. **`manualAltitudeM` 留空按 0 米算。** 界面的「留空表示不指定（写 null），不会被当成 0」只对经纬度成立；海拔走 `settings.ManualAltitudeM ?? 0`（`RelativeService.cs:414`），现象是目标相对高度整体带一个恒定偏差。
8. **尾迹填 0 不等于「后端不留轨迹」。** 屏幕当场不画尾迹，但后端保留窗口的下限是 **30 秒**——刷新页面后仍能回看最近半分钟；每轨点数上限仍是 `Math.Max(10, 秒数 × 5)`（尾迹 0 → 30 秒 → 150 点，`DeviceManager.TrackRetention`、`TrackStore.cs:23`）。跟踪目标数上限固定 300，不可配置；**点云帧不建目标拖尾**，只记无人机轨迹，避免几千个逐点 ID 冲爆目标表（`TrackStore.cs:74`）。
9. **改参考点或雷达安装会重置原点，改别的相对位置参数不会。** 只有 `referenceMode`、三个手动坐标或雷达安装参数变化才触发 `ResetReference()`（`DeviceManager.cs:228-241`）；相对位置配置的其余改动只做即时替换（`UpdateSettings`，`RelativeService.cs:67-74`）。存储会话目录的重建另有条件——只有**存储配置**变化时才会换会话目录（`DeviceManager.cs:206-224`）。前端在采集进行中会锁住这三个页签，就是为了避免参数一改把本次会话的落盘数据分成两段（`ConfigPanel.tsx:1654-1656` 注释）。
10. **`followReferenceDrift = true` 会让基座永远停在原点。** 原点每帧重新贴在基座当前位置上，基座定位漂移被吸收进其他设备的坐标，历史轨迹跨帧不再可比（`RelativeService.cs:402`）——排查「目标忽左忽右」时要先确认这一项的状态。

## 附录：配置文件的真实 JSON 形态

所有键都是 camelCase，枚举序列化为字符串（`PlatformConfig.cs:122-140` 与 `Program.cs:17-22` 的 JSON 约定，与 `frontend\src\types.ts:104-156` 一致）。随程序发布的 `backend\src\UavPlatform.Api\config\platform.json:183-217` 里 `relative` 段的初始内容为：

"relative": {
  "enabled": true,
  "referenceMode": "auto",
  "manualLongitude": null,
  "manualLatitude": null,
  "manualAltitudeM": null,
  "radar": {
    "mode": "coLocatedWithBase",
    "longitude": 0, "latitude": 0, "altitudeM": 0,

    "yawOffsetFromBaselineDeg": -90

  "filter": { "maxRangeM": 0, "minSnr": 0, "dropDeleted": true, "maxTargets": 4000 },

注意**这份随程序发布的配置文件与 C# 类的字段默认值并不完全一致**：`yawOffsetFromBaselineDeg` 是 `-90`（类默认 `0`）、`comparison.enabled` 是 `false`（类默认 `true`）。程序启动时读的正是这个文件（`PlatformService.cs:26-29`），因此**现场实际生效的是配置文件里的值**，界面上显示的也是它——遇到「跟默认值对不上」时先看这份文件。
