# 无人机 + RTK 平台上位机

面向「**基座（NebulasIV 高精度产品 / UM982）+ 雷达（NSR）+ 无人机载 GPS 模块（UCM221）**」三设备
一体化平台的上位机：**接入 → 实时解析 → 分级存储 → 同坐标系三维实时显示**。

现场布置（决定了本项目的坐标换算方式）：

- **基座与雷达装在一起**：基座是**双天线**，主天线给位置（RTK 定位），主天线与副天线连成一条
  **基线**并解出真航向（`$xxTHS`）；**雷达就架在两根天线中间**。
- **雷达正前方指向哪，由「相对双天线基线的夹角」这个安装输入 + 实时基线航向算出来**，
  于是雷达的探测方向能被实时标定到正北；由此再把雷达目标从「相对雷达」换算到「相对基座」。
- **无人机在空中飞，本身就是天上一个运动目标**：它通过 WiFi 模块用 **UDP** 把自身 GPS/姿态回传，
  给出的是**相对基座**的位置。
- 于是**雷达探测到的目标**与**无人机 RTK 回传的位置**被画进同一坐标系同框比对，
  用来判断雷达探得准不准（见第五节）。
- 后端 .NET 9 采集，前端 React 19 + React-Three-Fiber 三维显示，SignalR 高频推送。
- 三个设备的通讯参数、存储策略、显示坐标系基准全部可在界面上配置。

## 一、快速开始

**环境要求**（Windows）：

| 依赖 | 版本（本机实测） | 用途 |
| --- | --- | --- |
| .NET SDK | 9.0（实测 9.0.301） | 编译并运行后端 |
| Node.js + npm | ≥ 20（实测 v24.19.0） | 构建前端 |

`frontend\node_modules`、`wwwroot`、`bin/obj`、运行期 `data/` 都不进版本库，所以刚克隆下来
第一次跑时，`run.cmd` / `run.ps1` 会先自动装前端依赖（仓库里带 `package-lock.json` 就用
`npm ci`，否则 `npm install`）；连不上 npm registry 的机器，从别处复制整个
`frontend\node_modules` 目录即可。串口枚举走 Windows API，Linux / macOS 未验证。

```
run.cmd                 # 生产模式：构建前端到后端 wwwroot，启动后端，自动打开浏览器
run.cmd -Dev            # 开发模式：后端 + Vite 开发服务器（前端热更新），打开 http://localhost:5173
run.cmd -SkipBuild      # 跳过构建，直接用已有产物启动
run.cmd -NoBrowser      # 启动但不自动打开浏览器
```

PowerShell 用户可直接 `.\run.ps1`，参数同上。

- 生产模式地址：**http://localhost:5080**（前端产物由后端静态托管，只需一个端口）
- 开发模式地址：**http://localhost:5173**（Vite 把 `/api` 与 `/hubs` 代理到 5080）

> 改后端端口：`backend\src\UavPlatform.Api\appsettings.json` 的 `"Urls"`。

### 数据只来自真实设备

平台**没有内置数据源**：必须接上三台真设备（基座串口 / 雷达 TCP / 无人机 UDP），
再到界面点「**开始采集**」，三维视图与解析面板才会有数据。
早先那个「启动仿真」按钮与「仿真参数」条已按要求删除，所以没接硬件时界面会停在
「未采集 / 等待数据」——这是预期行为，不是故障。三台设备的通讯参数见下文
「现场接入三设备通讯参数」。

### 采集中参数是锁定的

点「开始采集」后，配置面板里的**通讯参数、存储参数、相对位置三页会整体变灰**，右下角
「保存并生效」一并禁用，面板顶部出现一条黄色提示。因为这三类参数一改就必须**把采集管线停掉重来**
——存储要换会话目录、设备要断开重连、相对位置要重置参考点，本次采集会被拦腰截断，
落盘数据分成两段、没法当成一次连续观测来对齐。

要改就先点「停止采集」，参数区会**自动恢复可用（不用刷新页面）**。锁定的只是参数本身：

- **界面显示开关**（显示目标 / 点云 / **无人机本身** / 轨迹 / 连线、跟随无人机、尾迹时长）与**三维视角切换**不受影响，采集中随时可调；
- 三个页签照样能自由翻看，折叠区块能展开收起，单个设备的「重连」按钮也照常可用；
- 「重算坐标系原点」这类**操作动作**（不是参数）同样不锁。

后端还有一道兜底：采集中直接 `PUT /api/config` 改这三类参数会返回 **HTTP 409**
（`采集中不能修改通讯、存储与相对位置参数，请先停止采集。`），并且**不会部分应用**，
配置内容与采集状态都保持原样——所以旧标签页、脚本、curl 也绕不过去。

## 三、现场接入：通讯参数怎么配

界面左侧「**参数配置 → 设备**」页签，三台设备各一张卡片。

> **参数说明默认不显示**：参数面板一屏要放几十个输入框，常驻的灰色说明会把真正要看的参数淹掉，
> 所以每条说明都改成**鼠标移到对应参数框（或键盘聚焦）时才弹出**、离开即消失；整段的说明文字
> 收成一个虚线「**说明**」标记，悬停或 Tab 聚焦才展开全文。设备卡片与「通讯参数 / 存储 / 相对位置」
> 三个子页签默认全部折叠，点「全部展开 / 全部折叠」可以一次性铺开或收起。

### 1. 基座（UM982）—— 串口

| 项 | 说明 |
|---|---|
| 串口 | Windows 下的 COM 口，如 `COM3`（设备管理器里确认） |
| 波特率 | **默认 460800**，与 `um982_driver` 的 `UM982_PORT_BAUDRATE` 一致 |
| 数据位/校验/停止位/流控 | 8 / None / One / None（8N1，驱动用 `cfmakeraw`） |

> **串口是下拉框，点哪里都会展开**：候选来自后端 `GET /api/serial-ports`（`System.IO.Ports.SerialPort.GetPortNames()`），
> 末尾固定有一项「**手动输入…**」——USB 转串口还没插上、或要多台机器共用同一份配置时，选它之后在
> **下面**多出一个手输框直接打字；下拉框本身**一直在**，想回列表不用先退出，在同一个下拉里点一项就切回去了。
> 鼠标移到这个框上会浮出「本机串口：COM1、COM2」之类的提示；
> 枚举失败或不插设备时，提示会明确说明「可手动输入」，不会静默给一个空下拉。
> 配置里已保存的串口名即使当前枚举不到，也会作为一项列在下拉里，不会被显示成「（未设置）」——
> 这一项后面缀着「**（配置里保存的，本机未检测到）**」，提醒它不是枚举出来的（例：配置里存着 `COM3`、
> 而这台机器只有 `COM1`/`COM2`，下拉里照样有 COM3 且处于选中态），鼠标悬停的提示里也写明这一点。

连接成功后上位机会按驱动行为下发输出配置（命令间 100 ms）：

```
gpgga com1 <间隔>
gprmc com1 <间隔>
gpvtg com1 <间隔>
gpths com1 <间隔>
saveconfig
```

`<间隔>` 默认 `0.05` = **20 Hz**，可在「UM982」分区改。
**看门狗**：GGA 或 RMC 任一超过 5 s 未更新且距上次重发超过 5 s，自动重发前 4 条（不含 `saveconfig`）。

> ⚠️ 串口是独占资源：本程序打开串口后会下发配置命令，**不能与其他模块共用同一串口**。
> ⚠️ 驱动从不修改模块波特率；波特率配错的现象是「收不到任何数据」而不是报错。
> ⚠️ `gpths` 真航向需要**双天线**；单天线时自动回退到 RMC/VTG 的地面航向。
> 排查双天线是否生效：看状态面板该设备的样本摘要里「真航向」是否出现，或直接抓 `$xxTHS`。

### 2. 雷达（NSR）—— TCP

**雷达是服务端，上位机是客户端**（协议 3.1 节）。

| 项 | 说明 |
|---|---|
| 主机 / 端口 | 雷达 IP 与端口，默认 `192.168.10.128:50000` |
| 本机地址编码 | `0x10`（协议 6.1：PC/上位机 = 0x10） |
| 雷达地址编码 | `0xFF` 广播；收到上传帧后自动学习源地址 |
| 连接后查状态 | 发 `0x0A` 读取雷达状态 |
| 心跳 | `0xA4`，默认 5 s 间隔 |

解析目标信息 `0xA8`（每目标 68 字节）与点云 `0xA9`（每点 68 字节，NSR800W 等型号目标输出走点云协议）。

### 3. 无人机 GPS（UCM221）—— 本机做 UDP 服务端

**无人机经 WiFi 模块用 UDP 主动把报文发到本机**，所以通讯方式选「**UDP**」，
本机在**所有网卡**上绑定监听端口，默认 **`8100`**（参数面板里的「本地端口」）。

> UDP 链路只认「本地端口」这一个绑定字段：后端 `UdpTransport` 用 `IPAddress.Any + LocalPort`
> 建 socket，所以界面上的「监听地址 / 监听端口」在 UDP 下并不生效——参数面板对 UDP 因此只给
> 「本地端口 + 远端主机 + 远端端口 + 允许广播」。「远端主机 / 远端端口」只在还没有收到过设备报文、
> 需要本机主动发包时作兜底目标（收到报文后会记住实际来源地址）。

上传流帧头 `0xA5 0x5A`，**所有数值字段按小端解析**（协议原文写「大端」，但真机抓包逐字节核对为小端，
详见 `docs/协议规格.md`）。本程序只取 GPS 相关的两个模块：

- **扩展信息模块**（`0xA33A`，45 B）：IMU + GPS 经纬高、速度、磁偏角
- **无人机信息模块**（`0xA22A`，39 B）：GPS 位置 + 相对高度 + 三轴速度 + 横滚/俯仰/航向

> ⚠️ 协议对扩展信息模块长度有两种印法（23 与 24 字节）；本实现以实测自洽的 **21 + 24** 为准，
> 解析器有交叉校验，长度不符会记日志并跳过该模块。

配置改完点「**保存并生效**」，后端会热更新：存储配置变了重建会话，相对位置配置变了重算参考点，
设备配置变了重建该设备的连接。

> **参数存在哪里（不会丢）**：运行时配置固定写在 `%LOCALAPPDATA%\UavPlatform\config\platform.json`
> （可用环境变量 `UAVPLATFORM_CONFIG` 指定别的路径）。工程里的 `backend\src\UavPlatform.Api\config\platform.json`
> 只是**出厂默认值**：首次运行时拷一份到上面那个位置，此后 `git pull`、改源码、`dotnet build` 都**碰不到**它。
> 这样无论用 `dotnet run`、`run.ps1` 还是直接双击 `bin\Release\net9.0\UavPlatform.Api.exe`，
> 读写的都是同一份配置——不会出现「换一种启动方式就换了一套参数」或「构建一次参数被抹掉」。
> 想恢复出厂参数，删掉用户目录那份重启即可（会重新播种）；`GET /api/health` 里能看到当前实际用的 `configPath`。

## 四、存储：五层落盘，每层都带设备时间与本地时间

会话目录（默认 `{后端程序目录}/data/{yyyyMMdd_HHmmss}/`，可选固定目录与自定义根路径）。
**默认模式下每次点「开始采集」都会新建一个会话目录**——包括「停止采集」后再开始，
所以两轮数据永远不会混进同一个目录、也不会从 `_0002` 接着上一轮续号；同一秒内连点两次
会用 `_2`、`_3` 后缀退让，不会合并。想一直写同一个目录就选「固定目录」模式：

```
data/20260929_120316/
├─ session.json            本次会话的配置快照、字段字典、统计
├─ session-summary.json    结束时写入的汇总
├─ 01_base_station/        ① 基座：原始字节 + 解析结果
│  ├─ raw_0001.bin         原始字节流
│  └─ parsed_0001.jsonl    解析后的 GnssSample
├─ 02_radar/               ① 雷达：原始字节 + 解析结果
│  ├─ raw_0001.bin
│  └─ parsed_0001.jsonl    解析后的 RadarSample（含全部目标/点云）
├─ 03_drone_gps/           ① 无人机：原始字节 + 解析结果
│  ├─ raw_0001.bin
│  └─ parsed_0001.jsonl    解析后的 DroneGpsSample
├─ 04_radar_base/          ② 雷达转基座系
│  └─ radar_base_0001.jsonl   每一帧雷达数据一条记录，目标坐标已换算到以基座为原点的 ENU
└─ 05_frame/               ③ 三设备同帧
   └─ frame_0001.jsonl       每一帧一条记录，基座 / 雷达 / 无人机在该帧的信息放在一起
```

上面的五组文件正好覆盖事后分析要用的**四类东西**，**没有跨设备的目标融合**——②③ 只是把各设备
**原始观测量**换算到同一坐标系后并排记录，不做目标合并，方便你用自己的算法重新处理：

- **① 分设备的原始数据 + 解析后的数据**：`raw_*.bin` 是设备真实字节，`parsed_*.jsonl`
  是解析结果（字段名与 REST / SignalR 完全一致），两者一一对应、可互相回放核对。
- **② 雷达转换到基座系的信息**（`04_radar_base/`）：**每一帧雷达样本写一条**，不节流，
  所以行数与 `02_radar/parsed_*.jsonl` 严格 1:1，雷达帧一条不丢。坐标固定为
  **以基座为原点的世界 ENU 系**，不随任何界面开关变化，这样跨会话、跨配置的数据可以直接对比。
  每条同时保留 `rangeM/azimuthDeg/elevationDeg` 原始观测量，便于核对换算是否正确。
- **③ 同一帧下三个设备一起的信息**（`05_frame/`）：每生成一帧写一条，把三个设备在同一帧里的
  位置、序号、数据年龄与雷达目标放在同一条记录里，是**跨设备对齐**的入口。
- **④ 每条记录都带两种时间**：`pcTime`（本机收到该数据的时刻，ISO 8601 带时区）与
  `deviceTime`（设备自己给出的时间，若协议携带）。②③ 的记录里除了本帧时间，每个设备还各自带
  `pcTime` / `deviceTime` / `sequence` / `ageMs`，做后处理时既可按 `pcTime` 按接收顺序对齐，
  也可按 `deviceTime` 按设备时钟对齐，不必再猜时间基准。

`session.json` 里的 `fieldDictionary` 给出了上述每一层每个字段的中文含义（`radarBase` 与
`frame` 两段），外部工具可以直接读它自解释。

- **按大小续文件**：单个文件超过「单文件上限」（默认 64 MB）自动新建 `xxx_0002` 续写，
  **不覆盖历史文件**（用 `FileMode.CreateNew` + 目录探测续号）。续号只在同一个会话目录内发生：
  默认模式下每轮采集都是新目录，所以每轮的第一个文件都是 `_0001`。
- **原始格式**可选 `binary`（记录为 `[int64 ticks][int32 长度][原始字节]`，可重放真实解析）、
  `hexText`（带时间戳的十六进制文本）、`text`（NMEA 原样）。
- **解析格式**可选 `jsonl`（每行一个 JSON，字段名与 REST/SignalR 完全一致）或 `csv`
  （雷达按「每个目标一行」展开，方便直接丢进 Excel / pandas）。
- 写入走内存缓冲 + 定时刷盘（默认 256 KB 缓冲、1 s 刷盘），采集循环不被磁盘 I/O 拖慢。
- **注意原始数据只在接真设备时产生**：`raw_*.bin` 的内容是设备**真实收到的字节**，
  由 `DeviceConnection.RawReceived` 触发（`DeviceManager.cs:417`）。平台**没有内置数据源**
  （早先那个「直接注入已解析对象」的仿真源已按要求删除），不接设备就没有任何样本，
  `raw_*.bin` 只会建出文件头、`parsed_*.jsonl` 也没有数据行。原始层本身的正确性由端到端测试覆盖：
  `端到端C_同一批样本应落成分设备原始解析_雷达转基座系_三设备同帧五类非空文件并保留关键字段`
  与 `端到端D_真实TCP回环_*` 都是把真实规格字节喂进真实解析器再断言落盘内容。
  设备卡片上的「保存原始数据」勾选框控制这一层是否开启，默认开启。
- **②③ 两层各有独立开关**：在「参数配置 → 存储」里的「保存雷达转基座系」与「保存三设备同帧」，
  默认都开启。关掉后对应的 `04_radar_base/` / `05_frame/` 目录不会被创建。

## 五、三维显示坐标系约定

用 ENU 切平面（东-北-天），**显示坐标系原点恒为基座**（世界 ENU 系：东 X+、北 Y+、天 Z+）：
基座与无人机输出的本身就是世界坐标（WGS84 → ENU），只有雷达目标报的是**本体极坐标**，
由雷达安装姿态换算进同一坐标系后，两者的轨迹才能逐点比对。

界面上**不再提供「以雷达为原点」的开关**。早期版本有「基座 / 雷达」二选一，但显示原点一旦可变，
落盘的相对位置数据就会随界面设置漂移、跨会话不可比；现在统一为基座世界坐标系，
雷达只作为「安装在某个已知位置与朝向的传感器」参与换算。

参数页里那个只读的「显示坐标系原点」文本框也一并去掉了（m06173 第 1 点）：它既不能改也不是参数，
真正的**实际**原点看顶栏的「**原点：…**」——基座还没定位时它会是「雷达」，帧里的 `reference.source`
会写明这一次取的是手动点、基座定位还是雷达位置。

> 📖 本节这些相对位置参数，每一个「用途 / 取值怎么选 / 代码里驱动了什么 / 设置错了会怎样」都逐项写在
> `docs\相对位置参数详解.md`：含参数总表、解算链路 12 步、参数→输出字段对照、4 种现场配置组合、
> 现场填写顺序与 10 条易踩的坑。配参数前建议先翻一遍。

- 雷达本体系到 ENU 的旋转：**+Y 为探测方向、+X 向右、+Z 向上**；
  顺序 Roll（绕本体 Y）→ Pitch（绕本体 X）→ Yaw（绕天向）。
- **雷达正前方（`Yaw`）有两个来源**，在「参数配置 → 相对位置 → 雷达安装 → 雷达朝向来源」里切换：
  - `baseHeadingPlusOffset`（**默认，现场用法**）：`正前方 = 基线真航向(THS) + 相对基线夹角`。
    夹角就是「雷达相对两根天线连成的基线装偏了多少度」这个安装输入；基线航向由基座双天线实时给出，
    于是基座转动或天线重新架设后，雷达的绝对朝向跟着自动更新。
  - `manualAbsolute`：直接手填探测方向相对正北的绝对夹角，用作双天线不可用时的兜底。
  > ⚠️ 只有 **THS（双天线真航向）** 会被当作基线航向。RMC / VTG 是**航迹向**，基座静止时它就是噪声，
  > 拿它去转雷达会把所有目标系统性转偏，因此这两种来源一律不采纳，自动回落到手动绝对角，
  > 并在状态面板注明原因（「航向来自 THS」或回退说明）。
- three.js 里的轴映射：**x = 东，y = 天，z = −北**，于是屏幕上方是正北、右方是正东。
- 雷达安装位置支持三种：与基座共址（默认，雷达就在两副天线的中间）/ 手动给定 WGS84 / 相对基座给东-北-天偏移。

界面同时给出：无人机相对基座的水平距离与相对高度、无人机到雷达的距离、雷达与基座的基线长度，
以及每个目标到无人机的距离与高度差。

### 雷达探测精度校核：无人机 vs 雷达

**无人机本身就是天上飞的一个运动目标**——雷达按自己的坐标系探到它，RTK 又给出它相对基座的真实位置，
两者换算进同一坐标系后就能逐帧算出雷达的测角 / 测距误差：

- 在雷达目标里取离无人机 RTK 位置**最近**的一个当作「无人机回波」；两者三维距离超过**匹配半径**
  （参数面板「雷达探测精度校核」里可改，默认 20 m）就判定「这一帧雷达没探到无人机」。
- 相对位置帧里因此多出 `droneComparison` 字段，给出**雷达 − RTK** 的偏差：三维距离差、水平距离差、
  斜距差、方位差、俯仰差，以及雷达侧与 RTK 侧各自的极坐标（距离 / 方位 / 俯仰），便于直接读数与标定。
  该字段为 `null` 表示本帧没有对比数据（未启用 / 参考点未解算 / 没有雷达目标）。
- 界面上：**无人机 RTK 用与雷达目标明显不同的形状与颜色**（菱形标记，雷达目标是圆点），
  两者之间画**偏差连线**并标注 Δ；连线偏离太近（屏幕上不足几像素）时改画「放大示意线」并把倍数写进标签，
  避免被误读成真实距离。雷达位置另有一条**朝向指示线**，尖端标出当前解算出的绝对角及其来源。
  三维视图与右侧「雷达解析」面板里都有。
- 不想要这套时，把「启用无人机 vs 雷达探测对比」取消勾选即可。

## 六、界面：三维视角、右侧解析面板、折叠与尾迹时长

### 三维视角：俯视 / 侧视 / 自由

三维视图左下角三个按钮切换视角：

- **俯视**：从正上方往下看，方位角固定（**不能旋转**），只能平移与缩放——用来看目标相对基座的分布。
- **侧视**：从正南方向平视，同样不能旋转——用来看高度与俯仰。
- **自由**：默认视角，可以**任意 360° 旋转**（含地平线以下），左键拖拽旋转、滚轮缩放、右键平移。

鼠标键位随视角走：**自由**里左键是旋转；**俯视 / 侧视**锁了旋转，左键就直接当平移用（否则按下去毫无反应——
这正是「三维视图平移不了」的那次投诉），中键与右键两个锁定视角里也一直是平移，滚轮始终是缩放。
左下角按钮旁边一直显示当前视角的键位提示；视图上的右键菜单已屏蔽，右键拖拽不会弹出浏览器菜单。

切视角或点顶栏「相机复位」都会把相机放回该视角的默认机位。勾选「跟随无人机」后，相机与注视点
**按无人机的位移增量一起平移**（视角本身不变，所以俯视跟飞、侧视跟飞都成立）：无人机不动时画面完全不动，
你自己拖出来的位置与角度不会被拉回去（早期版本是把注视点朝无人机插值，松手一秒内就滑回原处，
现场反馈的「平移后又回到原位置」就是这个）。视角选择记在浏览器本地，刷新后保持。

### 工具条上的显示开关

工具条从左到右：**目标** / **点云** / **无人机** / **无人机轨迹** / **目标尾迹** / **测距连线** /
**跟随无人机** / **尾迹输入框**。

- **无人机**（m06464 第 2 点新增）：只管无人机**本身**——四旋翼图标、光晕与洋红 RTK 位置标记
  （菱形 + 水平环）。取消勾选，天上那台机连同它的标记一起消失；
- **无人机轨迹 / 目标尾迹 / 测距连线**：各有各的开关，与「无人机」互不影响（关掉无人机本身后，
  它的轨迹与测距辅助线照旧画，除非把对应开关也关掉）。

无人机用一张 canvas 画的**四旋翼俯视图标**表示（`<sprite>` 公告板）：

- 俯视、侧视、自由视角看到的都是同一个清晰图标，不会像平面贴图那样在侧视时缩成一条线；
- **机头按航向自转**：航向是罗盘角（顺时针自北），程序把它投影到相机的成像平面上算出图标在屏幕里
  该转多少度，所以不管从哪个角度看，机头指的方向都对；
- 数据陈旧（超过 `staleTimeoutMs`）时图标整体压灰，**不隐藏**——「它还在那儿，只是数据不新了」
  和「它不在画面里」是两回事。三维区域**不放设备文字标签**：基座 / 雷达 / 无人机三台设备只有图标，
  陈旧了就把图标压灰，具体年龄写在左下角 HUD 的「⚠ 数据不新鲜」那行与状态面板里。

### 右侧解析面板：四个页签

左栏只放「参数配置 / 平台状态」两页，把人读的**解析结果**放到右栏，按设备分四个页签：

- **雷达解析**：最新一帧的命令字与目标数、触发来源、雷达位置与正前方角、基线航向；本帧目标表
  （目标号 / 类型 / **距离 / 方位 / 俯仰 / SNR**（雷达本体观测量）/ **东 / 北 / 天**（世界坐标系读数，
  基座未定位时该列写明「基座位置未解算」）/ 离无人机）；以及该设备的滚动解析原文。
- **基座解析**：链路与时间戳对齐、WGS84 位置、定位质量、解算出的世界系东-北-天、基线航向、姿态。
- **无人机解析**：GPS 位置与定位质量、世界系位置、距基座 / 高于基座 / 距雷达、航向、帧对齐。
- **运行日志**：链路、解析与存储事件（原来在左栏的那个日志页签，已挪到这里）。

「解析原文」就是后端逐帧生成的 `Summary` 文本——右栏看到什么，落盘就是什么。

### 面板折叠与长文本

- 左右两栏都能**收起**：左栏页签行的「收起 ◀」、右栏页签行的「收起 ▶」；右栏收起后留一条竖排按钮
  （点击即展开）。收起状态记在浏览器本地。中间不再有底部「解析样本」面板——它与右栏的解析文本是同一份数据。
- 参数面板里每一节标题行都可点击**折叠 / 展开**，采集中同样能折叠（锁定只锁输入框，不锁折叠）。
- 标题被省略号截断时，**鼠标悬停或键盘聚焦会浮出完整文字**（长设备名、长路径不用再猜）。
- 参数本身的文字**不再被裁**：左栏只有 372px 宽，早先写死 2/3 列的栅格会把「解析 RMC」挤成「解析」。
  现在列数随宽度自适应（窄了自动落成 1 列）、**下拉框独占一整行**（原生下拉的选中项文字截断了没法悬停查看，
  只能靠宽度）、开关文字允许折行（勾选框仍与第一行对齐）、长标签折行显示。

### 尾迹时长与断流清空

工具条上的「尾迹」是**数字输入框**（0 ~ 600 秒，默认取配置里的 60），决定轨迹点在屏幕上活多久：

- 超过这个时长的点**逐点消失**，而不是整条一起没了；
- 填 **0 就是不画尾迹**（已有的轨迹点当场全部过期），但无人机本身、目标球、测距辅助线都照旧；
- 某台设备**断流超过相对位置参数里的 `staleTimeoutMs`**（默认 3000 ms）后，该设备那条轨迹**整条清空**，
  避免把最后一个点一直留在屏幕上当作「它现在还在那儿」。

输入框里敲数字的过程**不发请求**：按回车、或点开别处（失焦）时才把值夹到 0 ~ 600 再保存。
到期判定在前端按每个点自己的时间戳做（`frontend\src\services\live.ts` 的 `tick()`），
改它**不会**重启采集管线，也**不影响落盘**——它改的是屏幕上的显示。

这条尾迹时长**同时**决定后端保留多少轨迹数据（供刷新页面后回看）：后端的保留窗口由它推出，
夹在 **30 ~ 600 秒**之间——填 0 时屏幕不画尾迹，但刷新后仍能回看最近 30 秒。
早先「重建轨迹参数」里那个单独的**「轨迹保留（秒）」已经删掉**：它和尾迹是同一个意思（轨迹活多久），
两个旋钮必然对不上——尾迹拉到 600 s、后端只留 60 s，刷新页面就只能回看 60 s。

### 没接任何设备时，怎么确认代码是对的

一句命令：

```powershell
.\selftest.ps1          # 等价写法：run.cmd -SelfTest
```

它把下面 8 层验证依次跑一遍，最后打一张通过/失败汇总表，**全程不需要真实设备**：

| # | 检查项 | 证明什么 |
|---|---|---|
| 1 | 后端构建 | 全部 C# 源码能编译，无语法/类型错误 |
| 2 | 后端测试 | 三套协议**用规格书真实字节向量逐字节喂入**，验证跨包分帧与字段解析；相对位置数学、坐标换算、滚动落盘都有断言 |
| 3 | 前端类型检查 | TypeScript 全量类型检查零错误 |
| 4 | 前端类名审计 | 组件用到的每个 CSS 类名都有定义（挡住上面说的静默错配） |
| 5 | 前端构建 | 能产出可被后端静态托管的产物 |
| 6 | 后端启动与页面托管 | API 起来、根路径返回页面、未知路径回落到 SPA |
| 7 | SignalR 冒烟 | 用与浏览器**完全相同**的客户端库连上 Hub，真实收到相对位置帧 |
| 8 | 真实浏览器渲染 | 真 Chrome 打开真页面：画布撑满容器、无未捕获异常 |

**必须说清楚它没覆盖什么** —— 别把绿灯当成「现场一定通」：

- 真实雷达的应答时序、真实 UM982 的双天线解算：没有硬件就无法覆盖；
- 真实串口的电气层与驱动行为：只验证到「能枚举出串口名」这一步；
- 现场网段的连通性（防火墙、IP 规划、路由）。

这三项只能接上真设备后按第三节逐项确认。

还有一条容易被误解的边界：**没接硬件时自测证明不了协议解析**。
平台没有内置数据源（早先那个把**已经解析好的对象**喂进管线的仿真源已按要求删除），
所以没接设备时自测只能证明到「Hub 连通、推送通路正常」这一步；字节级的正确性靠第 2 项
那几百个用例 —— 它们把真实规格字节喂进**真实分帧/解析器**，两者合起来才覆盖整条链路。

### 前端测试怎么跑

`frontend\tests\` 下的 UI 冒烟测试用的是**从真实后端抓下来的 fixture**
（`frontend\tests\fixtures\*.json`），不是手写的假数据，目的是让测试里的数据结构
与真机一致 —— 尤其是那个反复踩的坑：`PlatformConfig` 里的枚举是 `camelCase`
（`"kind":"baseStation"`），而 `status.devices[].kind/state/transport` 是
`PascalCase` 字符串（`"BaseStation"`）。契约一旦变了，重抓 fixture 即可：

```powershell
# 后端跑着（http://localhost:5080）时执行，会重新抓取并裁剪 fixture
cd frontend; npm run fixtures
```

覆盖范围：`ConfigPanel` / `StatusPanel` / `SampleTable` 三个面板与 `App` 外壳的真实挂载
（含页签切换、草稿与已保存配置的隔离、基准设备切换）。

**jsdom 覆盖不到三维视图**：`Viewer3D` 要 WebGL，jsdom 没有实现，所以它在 `App` 用例里被
替换成占位元素，只由 `tsc` 与打包把关。这留过一个真实缺口 —— `Viewer3D` 的 HUD 是渲染在 `<Canvas>` **之外**的 DOM 叠加层，
却调用了 R3F 的 `useFrame`，R3F 抛
`Error: R3F: Hooks can only be used within the Canvas component!`，
整棵 React 树随之卸载，页面上只剩 body 的深色背景，**看起来就是「整个网页都是黑的」**。
类型检查与打包都不会报错，只有真跑一次浏览器才看得见。

所以补了一个**真实浏览器渲染冒烟**，无头 Chrome 打开真实页面，断言
「无未捕获异常、`#root` 有内容、页面上有 `<canvas>`」，并打印 HUD 文本与页签：

```powershell
# 需要后端已在 http://localhost:5080 运行
cd frontend; npm run smoke:ui
```

它同时会打印页面上的 HUD 文本（原点、无人机 ENU、离基座/离雷达距离、目标数、相对位置频率），
用来一眼确认三维视图确实拿到了实时数据。另有独立的后端推送冒烟脚本，用与浏览器完全相同的
SignalR 客户端库验证实时链路：

```powershell
cd frontend; npm run smoke:hub
```

**布局类缺陷同样只有真浏览器看得见。** `smoke:ui` 除了判断「页面是否活着」，
还会打印各区域的 `getBoundingClientRect()` 与每个 `<canvas>` 的 CSS 尺寸 / 绘制缓冲尺寸，
并断言三维画布至少占满其容器的 90%。这条断言来自一个真实缺陷：`Viewer3D` 渲染的是
`<div className="viewer3d">`，而样式表里写的选择器是 `.viewer-wrap` —— 名字对不上，
容器就完全没有样式、高度塌成 `auto`，R3F 的 `height:100%` 无处可解析，
画布退化成 HTML 默认的 `300x150`，表现是**三维区域只有 150px 高、下面一大片黑**。
根因与修法见 `frontend\src\index.css` 里 `.viewer3d` 上方的注释。

为在构建前就挡住这类静默错配，另有一个类名审计脚本，静态比对「组件用到的类名」
与「CSS 定义的类名」：

```powershell
cd frontend; npm run audit:css
```

它分别列出「组件用了但 CSS 未定义」（退出码 1，是真 bug）与「CSS 定义了但没人用」（死代码）。

### 本机环境注意事项

- 解决方案文件是 **`.slnx`**（不是 `.sln`）：`.sln` 会被本机 DLP 透明加密成
  `%TSD-Header-###%` 导致 `error MSB5010: 未找到文件格式头`。
- `System.IO.Ports` 在 net9.0 **不在基础框架内**，必须显式引用 NuGet 包 `8.0.0`（已在 Core 工程里）。
- 本机离线（nuget.org 与 npmjs.org 均不可达），包版本必须落在本地缓存内；
  `frontend\node_modules` 是从参考项目复制的，**不要删除**。
- 写文件不要用 `python.exe` / `node.exe` 直接落盘（会被 DLP 加密成 `%TSD-Header-###%`）：
  让它们写 stdout，再由 PowerShell 用 `[System.IO.File]::WriteAllText` 落盘。

## 九、项目背景与现场确认结果

**项目性质**：本系统是**无人机静态真值评估系统**。基座与雷达装在一起、静止架设在地面，
基座双天线给出 RTK 定位与真航向，构成静止的地理真值基准；**无人机是唯一的运动目标**，
通过 WiFi 模块用 UDP 把自身 GPS 定位回传，由本系统接收。三者的数据最终统一到同一坐标系，
既用来观察无人机轨迹与其定位质量，也用来把**雷达探测到的无人机回波**与 RTK 真值逐帧比对。

据此确定的现场配置（已核对源码，无需改动）：

| 项目 | 结论 | 源码依据 |
|---|---|---|
| 基座天线 | **双天线**，THS 真航向可用 | `backend/src/UavPlatform.Core/Models/DeviceConfig.cs:173` `UseTrueHeading = true`（已默认启用） |
| 雷达链路 | **TCP 客户端**，目标数据按 `0xA8`（每目标 68 字节）解析 | `backend/src/UavPlatform.Core/Protocols/NsrRadarProtocol.cs` |
| 雷达朝向 | 默认「基线真航向(THS) + 相对基线夹角」，可切手动绝对角 | `backend/src/UavPlatform.Core/Models/RelativeConfig.cs` `RadarYawSource.BaseHeadingPlusOffset` / `ResolveYawDeg()` |
| 雷达安装位置 | 默认与基座**同点**（雷达在两副天线中间，基线恒为 0） | `backend/src/UavPlatform.Core/Models/RelativeConfig.cs:39` `RadarPlacementMode.CoLocatedWithBase` |
| 无人机链路 | **UDP**，本机在所有网卡上绑定 `8100` | `backend/src/UavPlatform.Core/Devices/Transports.cs:185` `new IPEndPoint(IPAddress.Any, _settings.LocalPort)` |
| 对比校核 | 相对位置帧带 `droneComparison`，偏差定义为**雷达 − RTK** | `backend/src/UavPlatform.Core/Relative/RelativeService.cs` `BuildDroneComparison(...)`；默认匹配半径 20 m |

仍需接真机时填写的项：

1. 基座串口在 Windows 下的实际 **COM 口**（默认写的是 `COM3`；双天线已确认）。
2. 雷达的 **IP / 端口**（默认 `192.168.10.128:50000`）。
3. 确认无人机 WiFi 模块的**目标地址就是本机的 `8100`**（UDP，需与本机在同一网段）。
4. **雷达相对双天线基线的夹角**：安装后量一次填进「相对基线夹角」。基线航向由 THS 实时给出，
   因此不必再手填雷达的绝对朝向（除非双天线不可用，才切到手动绝对角兜底）。
